1. 概要・目的

Salesforce Experience Cloud（Aura）の診断では、「同じ操作の通信が何度も重複していないか」「どのパラメータにワードリストの語がヒットしたか」「Burpの履歴エクスポートと後で突き合わせられるか」を、診断作業のその場で確認したい場面が多くあります。

python/burp_to_csv.py はこれをXMLエクスポート後にまとめて処理するCLIツールですが、本プラグインは同一のロジック（分類・Aura集約キー・ワード照合）をBurp上でリアルタイムに実行し、次を実現します。

  1. 採番：各パケットのCommentに固定番号を記入し、後でXML出力した際にBurpの履歴とburp_to_csv.pyの出力を対応付けられるようにする
  2. Aura集約判別：同一操作の繰り返し通信（フォーム逐次送信等）を「代表／集約対象／単独」で判別し、予約色でオンデマンドに可視化する
  3. ワード照合：GUIで登録したCSV（word.csv互換）で、選択中パケットのどこにどの語がヒットしたかをその場で確認する

これらの結果はComment欄への追記を通じてSave items(XML)経由でburp_to_csv.pyの出力と突き合わせ可能です。ユーザー自身の色分け作業やComment欄の既存メモには一切自動介入しません（すべてボタン操作によるオンデマンド実行）。

2. 導入方法

2.1 Jython のセットアップ

1jython-standalone.jar をダウンロード（バージョン 2.7.x を推奨）
2Burp Suite → Extender → Options → Python Environment
3"Location of Jython standalone JAR file" に、ダウンロードした jar のパスを設定

2.2 拡張のロード

1Burp Suite → Extender → Extensions → Add
2Extension type: Python
3Extension file: sf_aura_burp_helper.py を選択
4Next → エラーが出ないことを確認（Errorsタブも確認）
5ロードが成功すると、Burpのタブに "SF Helper" が追加されます
日本語を含むフォルダパスでロードすると、JVMの文字コード設定次第で OSError: (2, 'No such file or directory', ...) のようなエラーになることがあります。その場合は、拡張ファイルをASCII文字のみのパス（例: /Users/xxx/burp-extensions/）にコピーしてから読み込んでください。

4. コックピット タブ

診断中に何度も使う操作を1画面にまとめたタブです。「Auto実行」の枠と「個別操作」の枠が上下に並びます。

4.1 Auto実行

チェックボックス2つで事前にオプションを選び、[▶ Auto実行] を押すと、以下をこの順番で自動的にまとめて実行します。

(追加コメント全クリア ※チェック時のみ) → 採番 → 解析更新 →
(集約対象へ予約色を適用 ※チェック時のみ) → 解析結果をCommentへ追記
  • [▶ Auto実行] を押すと、まずルール（ワードリスト）のインポート状況を確認するダイアログが出ます。読み込み済みなら件数を表示、未読み込みなら「ワード照合は常に該当なしになります」という警告付きで表示され、実行/中断を選べます。
  • 「実行前に追加コメント全クリアを行う」：既定でON。チェックすると、Comment内の [ ... ] をすべて削除する処理を先に行います。元に戻せない操作のため、確認ダイアログが必ず出ます（ONのままでも誤操作にはなりません）。
  • 「解析後に集約対象へ予約色を適用を行う」：既定でON。解析更新の直後に予約色を適用します。色そのものは[集約色]タブの設定を使います。
  • 採番の接頭辞・桁数・開始番号は[採番]タブの現在の設定を使います。各ステップは既存の各ボタンとまったく同じ処理を順番に呼び出すだけなので、個別実行と結果が変わることはありません。

4.2 個別操作

1つずつ実行したい場合のショートカットです。ボタンと説明を1行ずつ並べたグリッドで、各タブに元々あるボタンと同じ処理を呼び出します。

解析更新Proxy history 全件を再解析し、集計・一覧を更新します
解析結果をCommentへ追記集約判定・ワード照合の結果をCommentへ追記します
集約対象に予約色を適用「集約対象」のパケットにのみ予約色を適用します
予約色のみクリア現在「予約色」になっているパケットのハイライトだけを解除します

5. ルール タブ（ワード照合の設定）

画面は上下2段に分かれています。① リクエスト用ルール（上段）と② レスポンス用ルール（下段）はそれぞれ完全に独立した表・ボタン群・AND/OR設定を持ちます（実行ログだけは共有）。上段はパス・クエリ・リクエストヘッダ・リクエストボディを、下段はレスポンスヘッダ・レスポンスボディを照合対象にします。同じVuln-Noを両方の表に定義することもでき、その場合は[解析]タブ・Commentへの追記マーカー上では1件のVuln-Noとして（両方のヒット箇所をまとめて）表示されます。

1各段の [CSVロード...] ボタンで word.csv（または独自作成のCSV）を読み込みます（上段＝リクエスト用、下段＝レスポンス用として個別に読み込みます）
2読み込んだ内容は各段の表に展開され、直接セルを編集できます
3編集後は各段の [表からルール反映] を押して確定してください（押さないと編集内容は使われません。上段・下段それぞれ個別に反映が必要です）
4結合条件 は各段の AND / OR ラジオボタンで切り替えます（既定 AND、上段・下段で独立して設定可能。例：リクエスト側はAND、レスポンス側はOR、という組み合わせも可能）
文字コードは自動判定します（UTF-8[BOM可]を優先し、デコードできない場合のみ cp932[Shift_JIS系]にフォールバック）。comment列に日本語を入れて読み込んだ際、ログに「文字コード: UTF-8」等の判定結果が表示されます。
セルを入力した直後（Tab/Enterで確定する前）に[表からルール反映]を押しても、直前の入力が正しく反映されます。[行追加]で新規行を作ってすぐ入力→反映、という使い方をしても、最後のセルの入力が抜け落ちることはありません（Swingの仕様上、ボタンクリックだけではセル編集が自動確定しないため、内部的に明示的な確定処理を行っています）。wordlist1/wordlist2・Vuln-No・commentのいずれも、日本語を含めて問題なく使えます。

5.1 ヒット状況・ヒット数の目印

各段の表の5列目に 「ヒット状況」、6列目に 「ヒット数」 列があります。[解析]タブで [解析更新] を実行するたびに、その回の解析結果に基づいて 「ヒットあり」 または 「★ 未ヒット」 の目印と、そのVuln-Noにヒットしたパケット数（1パケット内で複数箇所ヒットしても1件と数える）が自動的に付きます（解析未実施、またはCSVを読み込み直した直後はそれぞれ - / 0 のまま）。

「★ 未ヒット」のルールは、一度もどのパケットにもヒットしていないことを意味します。ワードの綴りが違う・そもそも対象の通信が発生していない等の見直しに使ってください。この判定は、[解析]タブの範囲指定・[集約対象を除いて表示]チェックとは無関係に、解析対象全体を基準にしています（表示を絞り込んでいるだけのヒットを「未ヒット」と誤判定しないため）。リクエスト用・レスポンス用のヒット状況／ヒット数はそれぞれ独立に集計されます。未ヒットの一覧表示はこの[ルール]タブの表のみで、[解析]タブ側には表示しません。

5.2 CSVの形式（2パターン対応、comment列は任意。リクエスト用・レスポンス用とも同一形式）

パターンA：ヘッダ付き形式（+ 任意で comment 列）

Vul-No,Method,param,comment
1,QrCode/CAS_CTRL_MH024,customerNumber,認可不備の疑い。要手動確認
2,_nc_external/hoge,buster,

→ ヘッダのいずれかの列名に「vul」を含む列を自動検出し、それを Vuln-No 列とみなします。同様に列名に「comment」を含む列があれば comment 列として扱います。残り2列は左から右の順で wordlist1 → wordlist2 です。comment列が無い（3列だけの）CSVもそのまま読み込めます（comment欄は空になります）。

パターンB：ヘッダなし、位置指定形式（+ 任意で4列目）

recordId/accountId,GET/POST,V-001,このパターンは要注意
reqJson/filter,POST,V-002

→ 1列目が wordlist1、2列目が wordlist2、3列目が Vuln-No、4列目があれば comment です（無い行はcomment欄が空。行ごとに列数が違っても問題ありません）。

いずれの形式でも、各セル内は / 区切りで複数ワードを指定でき、同一リスト内は常にOR判定です（例: recordId/accountId は「recordIdまたはaccountId」の意味）。/区切りはwordlist1・wordlist2専用で、comment列は自由記述のテキストとして扱われます。

comment列の使いみち：ルール表・[解析]タブのワード照合一覧の両方に、この列の内容がそのまま表示されます（例: 「認可不備の疑い、要手動確認」）。Burp の Comment（採番・集約マーカー等）とは別物です。

5.3 判定ロジックと照合範囲

(wordlist1のいずれかがヒット) [AND または OR] (wordlist2のいずれかがヒット)
  • AND（既定）: burp_to_csv.py --word-list と同一の判定
  • OR: どちらか一方のリストにヒットすれば成立する、より緩い条件（本プラグイン独自の拡張）

ワイルドカード（*）

wordlist1・wordlist2のセルに * を1語として指定すると、そのリストは常に条件成立したものとして扱われ、実際にコーパス中で * という文字列を探すことはしません。片方のリストだけで判定したい場合に使います。

Vul-No,Method,param
1,*,isAdmin

→ wordlist1（この例ではMethod列）が * なので無条件成立、isAdmin が見つかるかどうかだけでVuln-No 1のヒットが決まります。

ワイルドカードを含むルールは、AND/OR設定に関わらず、常にAND相当で判定されます。 素直に「OR」のまま評価すると、ワイルドカード側が常に真になるため、(常に真) OR (isAdminの一致) はもう一方の条件を一切確認せずに常にヒットしてしまいます（意図しない緩さ）。これを避けるため、ワイルドカードが絡むルールは結合条件（AND/OR設定）を無視して常に (常に真) AND (isAdminの一致) として判定します。AND/OR設定を「反転」させたような形になりますが、これは「ワイルドカードでない側の実際の一致結果だけでヒットを判定したい」という意図を、OR設定時にも一貫して成立させるための挙動です。burp_to_csv.py側は元々AND固定のため、この反転自体は発生しません（ワイルドカード側が常に真になるだけです）。同一リスト内の他の語と * を併記した場合（例: */foo）も、OR判定の性質上 * が1つでもあればリスト全体が無条件成立になります。

照合範囲は、① リクエスト用ルール（上段）＝リクエストパケットの パス・クエリ・リクエストヘッダ（Cookie含む）・リクエストボディ、② レスポンス用ルール（下段）＝レスポンスヘッダ・レスポンスボディです。レスポンスは分類判定にも引き続き使用されます。

レスポンス用ルールの照合では、リクエストボディの message= パラメータのようなURLデコードは行いません（レスポンス本文はURLエンコードされている前提がなく、誤ってデコードすると本来の + 等の文字を壊してしまうため）。
実装方式：照合は Insertion Point（キー単位への分解）ではなく、対象テキスト全体を1つの文字列としたシンプルな部分文字列検索です。JSONがどれだけネストしていても、キー名や値はテキスト上では連続した文字列として存在するため、階層に関係なくワードを検出できます（JSONパース失敗や二重シリアライズの影響を受けません）。ただし Aura の message= パラメータ（リクエストボディ側のみ）はURLエンコードされたJSONのため、照合前にURLデコードしてから検索します（デコードしないと :// や " のような記号を含むワードが生テキスト上の %3A 等と一致しなくなるため）。

6. 解析 タブ

[解析更新（HTTP history全件を再解析）] を押すと、現在の Proxy history 全件を解析します（バックグラウンド実行のため、Burpの操作は継続できます）。

6.1 Scope による絞り込み

[Burp Target Scope 内のみを解析対象にする] をチェックすると、Burpの Target タブ → Scope の設定（callbacks.isInScope）で対象URLを絞り込みます。

既定でON です。先にBurpのTargetタブでScope（Include in scope）を設定してから使ってください。 Scopeを何も設定していない状態のままだと解析結果が0件になります（その場合はログに「全件がScope外と判定されました」というヒントが出ます）。Scopeを使わない場合はチェックを外せば従来通りhistory全件が対象になります。

URL取得やスコープ判定自体に失敗した場合は、安全側（除外しない）に倒します。チェックの変更は次回の[解析更新]から反映されます。この絞り込みは解析（集計・一覧・集約色適用・Commentへの追記）にのみ適用され、①採番には影響しません（採番はburp_to_csv.py側のNo/Comment対応付けに使うため、history全件が対象のまま一貫させています）。

6.2 種別ごとの集計

分類（画面／画面更新(SPA)／API／静的）ごとの件数と合計を表示します。個々のパケットのAggKey/AggRole/Descriptors等は、選択パケットの "SF Vuln/Agg" タブで確認します。

  • 表示対象の採番範囲を、①採番タブで振った番号（[0001]〜等）で絞り込めます。空欄のまま [表示を更新]（または解析更新後）で全件対象。範囲指定時、まだ採番していないパケットは対象から除外されます。この範囲指定は下の「ワード照合 一覧」にも同じ範囲で適用されます。
    From/Toは手入力のほか、Proxy historyでパケットを右クリック→「SF Helper: [解析]表示範囲のFromにこの採番番号をセット」／「...のToにこの採番番号をセット」でも設定できます。対象パケットのComment先頭の採番番号を読み取ってそのままFrom/To欄に入力するため、数字を見て手入力する必要がありません。複数選択時は先頭の1件を使用します。セットすると（解析済みであれば）即座に集計・一覧が再フィルタされます。未採番のパケットを選んだ場合はその旨がログに出ます。
  • 件数は「集約対象を含む」「集約対象を除く」の2列で並べて表示します。「含む」は履歴上のパケットをそのまま数える件数、「除く」は集約対象を除いた件数（＝代表+単独のみ。実質的な「操作の種類の数」に近い値）。画面／API／静的は集約判定の対象外のため、この2列は常に同じ値になります（集約対象になり得るのは画面更新(SPA)のみ）。
  • 表の下の「表示対象: N / M パケット」の N は、下のワード照合一覧の[集約対象を除いて表示]チェックの状態に連動します。ONなら「除く」列の値、OFFなら「含む」列の値になり、チェックを切り替えると即座に数字が変わります。M（分母）は採番範囲・Scope絞り込み後の総パケット数です。このNは「パケット数」であり、下のワード照合一覧の「行数」（＝ヒット件数）とは単位が異なります（1パケットが複数のVuln-Noにヒットすれば複数行になるため）。

一度もヒットしなかったVuln-Noの確認は、[ルール]タブの表の「ヒット状況」列（§5.1）で行います。[解析]タブ自体には未ヒットの一覧は表示しません。

なぜ「画面」の件数が「画面更新(SPA)」より多くなるのか：

分類は classify() 関数が次の優先順位で判定しています（burp_to_csv.py と同一ロジック）。

  1. パスに auraAnalytic を含む → API
  2. パスにAura関連のマーカー（/aura, sfsites/aura, auraCmpDef, auraResources）を含む、またはボディに message=/aura.context= を含む → 画面更新(SPA)
  3. 拡張子/レスポンスMIMEが静的アセット相当 → 静的
  4. レスポンスMIMEが html を含む → 画面
  5. どれにも該当しない → API

「画面」は、Auraの操作でも静的アセットでもないHTMLを返すリクエストすべてが該当します。ページ遷移・リロードは、Auraアクションを何も呼ばなくても1件ずつ計上されます。一方「画面更新(SPA)」は実際にAuraアクションが呼ばれた通信だけが該当するため、サイトを巡回・閲覧しただけでフォーム操作をあまりしていない場合は「画面」が上回るのが自然です。

6.3 ワード照合 一覧

各列見出しをクリックするとその列でソートできます（もう一度クリックで昇順/降順切替）。例えばVuln-No列でソートして同じ脆弱性のヒットをまとめて確認する、といった使い方ができます。Vuln-No列は文字列の辞書順（1,10,3のような順）ではなく、数値としての自然順（1,3,10）でソートされます（SEC-1のような数値以外を含む値が混在していても、数値部分だけを数値として比較するため破綻しません）。

列は次の順で表示されます。

Comment / AggRole / Method / URL / 分類 / Vuln-No / ヒット元 / ヒットしたワードとロケーション / ルールComment
列内容
CommentBurpの Comments 欄の内容（内部の通し番号Noはhistory上の表示と対応しないため列に出さない）
AggRole「代表／集約対象／単独」。Comment列のすぐ次に配置し、専用タブを開かなくても集約対象かどうかを判別できるようにしている

見出しの横にある [集約対象を除いて表示] チェックボックス（既定でON）で、AggRoleが「集約対象」の行を一覧から非表示にできます。同一操作を繰り返しテストすると集約対象の行が代表と同じ内容で埋まりがちなため、まず代表・単独だけの実質的な一覧を見せる運用です。チェックの変更は解析済みであれば押した瞬間に反映されます。

表の下に 「選択行: ヒットしたワードとロケーション」「選択行: ルールComment」 という2つの表示欄があります。表の行を1つクリックすると、その行の内容がそれぞれの欄に表示されます。
  • 「ヒットしたワードとロケーション」欄は ロケーション → ヒットしたワード の順の2列を持つ小さな表で、ヒット1件につき1行で表示します（1行のテキストに詰め込みません）。
  • 「ルールComment」欄は長文でも折り返して表示するテキストボックスです。テーブルのセルは列幅を広げないと長文が見切れますが、この欄はスクロール可能で文章が切れません。
行を選択すると、その行のComment先頭にある採番番号（例: [0005]）が自動的にクリップボードにコピーされます。 BurpのAPIには拡張からHistoryタブの検索窓へ直接値をセットしたり、該当行を選択・スクロールしたりする手段が存在しないため、コピー＆手動貼り付けで代替しています。コピー後、Burpの Proxy > HTTP History タブに切り替えて検索窓（虫眼鏡アイコン）に貼り付ければ、該当パケットをすぐに絞り込めます。採番されていないパケットの行を選択した場合は何もコピーされません。

ワード照合一覧のCSV出力

見出しの [この一覧をCSV出力...] ボタンを押すと、その時点で一覧に表示されている行（採番範囲の絞り込み・[集約対象を除いて表示]チェックの状態がそのまま反映されます）をCSVファイルに保存します。保存先は都度ダイアログで選択します。

出力される列は次の通りです。

Comment / AggRole / Method / URL / 分類 / Vuln-No / ヒット元 / ヒットしたワード@ロケーション / ルールComment / Request / Response

先頭8列は画面のワード照合一覧と同じ内容です（「ヒット元」列でそのVuln-Noが①リクエスト用ルール／②レスポンス用ルールのどちらでヒットしたかがわかります）。加えて、該当パケットの Request と Response（生のリクエスト/レスポンス全体）を列として追加します。

Comment列は、Burp上のComment欄の内容から、本ツールが末尾に追記する解析マーカー（[SF Cls=... Vuln(N件): ...] 等。6.4「解析結果をCommentへ追記」で書き込まれる部分）を取り除いたものを表示します。①採番の番号（例 [0005]）とユーザーが手で書いたコメントまでが対象で、本ツールが自動追記した部分は含みません。

Excelでの閲覧を想定し、Request/Responseは次のように整形されます。

  • 改行（\r\n \n \r）はすべて半角スペースに置換し、1パケット=1行に収めます。
  • 長さが500文字を超える場合は先頭500文字で切り詰め、<---snip--->という目印と(全N文字)という元の文字数を末尾に付記します（省略されたことが一見してわかるようにするためで、省略された内容自体はCSVには含まれません。全文が必要な場合はBurp上で該当パケットを直接確認してください）。
  • 文字コードはUTF-8（BOM付き）で保存するため、Excelでそのまま開いても文字化けしません。

ヒットが無いパケットは出力対象外です（画面の一覧と同じく、Vuln-Noにヒットした行のみが対象になります）。1パケットが複数のVuln-Noにヒットしている場合は、画面表示と同様にVuln-Noの数だけ行が分かれます。

6.4 解析結果をCommentへ追記（集約判定＋ワード照合）

[解析結果をCommentへ追記] ボタンを押すと、解析済みの全パケットのComment欄末尾に、次の形式で情報を追記します。

[SF Cls=画面更新(SPA) Agg=集約対象(size=3)→代表[0005] Vuln(1件):

[SF Cls=画面更新(SPA) Agg=代表(size=3)]
[SF Cls=API Agg=単独 Vuln(2件):

要素内容
Cls=必ず書き込まれる。画面／画面更新(SPA)／API／静的の4分類のいずれか。burp_to_csv.pyの「分類」列と完全に同じ表記
Agg=必ず書き込まれる。代表 / 集約対象(グループ件数) / 単独 のいずれか
→代表[NNNN]集約対象の場合、代表パケットの現在のComment先頭の採番番号を参照。未採番なら(未採番)
Vuln(N件):ワードリストにヒットしたパケットにのみ付く（無ければ省略）。ヒット件数が1件でも複数件でも常にこの見出し＋改行形式で統一している（1件だけの場合と複数件の場合で書き方が異なると見た目で気付きにくいため）。1件ずつ改行し、行頭に・を付けてVuln-No(語@場所, ...)[ルールComment]形式で列挙する。見つかったVuln-Noと、実際にヒットした単語・場所に加え、word.csvのcomment列（設定されていれば）も末尾の[...]に記録する。comment列が無い／空欄のルールではこの部分は付かない（§5.1のルールComment列と同じ内容・優先順位）

既存のメモ内容は保持され末尾に追記されます（採番はComment先頭を使うため衝突しません）。何度実行しても前回このボタンが書いたマーカーを検出して置き換えるため、重複追記されません（冪等）。

推奨手順：①[解析更新] → ②[採番]タブで[全history採番] → ③再度[解析更新] → ④[解析結果をCommentへ追記]。この順で行うと代表の番号が確実に反映されます。
解析は「実行した時点」の history 順序に基づきます。後からトラフィックが増えるとグループの内容（size等）が変わることがあるため、採番・集約色適用・Comment追記の直前に必ず[解析更新]を再実行してください。

7. 採番 タブ

  • 接頭辞・桁数・開始番号 を指定し、[全history採番] を押すと、Comment欄の先頭に [0001] のような番号が追加されます（既存のメモ内容は保持）。
  • 既に採番済み（同じ接頭辞のパターンで始まる）パケットはスキップされます（再実行しても安全）。
  • [採番解除（全history）] で、先頭の番号部分だけを取り除きます。
  • 右クリックメニューからも、選択したパケットだけに採番できます。
  • [追加コメント全クリア（[ ]を全削除）] で、Comment内の [ ... ] 形式の部分をすべて（先頭の採番トークン・末尾の解析マーカー・入れ子含む）まとめて取り除きます。本ツールは書き込みを常に [ ] で囲む設計のため、逆に「[ ]で囲まれたものを消せば本ツールが追記した分だけをまとめて取り除ける」という考え方です。手動で [ ] を使ったメモも区別なく削除されるため、実行前に確認ダイアログが出ます（元に戻せません）。
運用のコツ：番号は「実行時点のhistory順」で決まります。トラフィック取得が完了してから、Save items でXML出力する直前に採番することを推奨します。これにより、番号とburp_to_csv.pyが出力するNo列がズレなく対応します。

8. 集約色 タブ／Aura集約の根拠

Auraのフォーム逐次通信のように、同じ操作が何度も繰り返されている通信を見分けるための機能です。

1予約色 を選択します（ご自身の色分け作業では使っていない色を選んでください。既定は gray）
2[集約対象に予約色を適用（オンデマンド）] を押すと、[解析]タブで判定済みの「集約対象」にだけ予約色が適用されます
3[予約色のみクリア] を押すと、現在その予約色になっているパケットの色だけを解除します（他の色には触れません）

どちらのボタンも押した時だけ動作します。適用前に必ず [解析] タブで [解析更新] を実行しておいてください。

8.1 集約キー（AggKey）の考え方

「集約対象」の考え方は burp_to_csv.py と同一です。同一のAuraアクション・対象オブジェクト・呼び出し元画面・認証状態から成る通信グループのうち、最初の1件（=代表）以外を「集約対象」と判定します。

通信の種類AggKeyに含む要素
Aura（descriptorあり）パス／descriptor／対象オブジェクト／pageURI／認証状態
Aura（descriptorなし。auraCmpDef等）パス／パラメータの値まで含めた内容／認証状態
画面/API/静的常に「単独」（集約判定の対象外）
集約対象になり得るのは Aura の SPA通信（画面更新(SPA)）だけです。 それ以外の通信（画面/API/静的。例: /cst/s/otc のようなワンタイムトークンを含むリクエスト等）は、method+pathだけの粗いキーになり無関係な別リクエスト同士を誤って同一グループに丸めてしまうリスクがあるため、常に「単独」として扱われます。
Aura SPA通信のうち、descriptorを持たないもの（auraCmpDef/auraResources等のコンポーネント定義取得のようなGETリクエスト）も集約対象に含まれますが、この場合はパラメータの値まで含めて内容が完全に一致する場合のみ同一グループとみなします。名前だけが同じでも、値（実際に読み込んでいる内容）が違えば別グループのままです。

8.2 隣接性の条件

なぜ「隣接している範囲だけ」を1グループとみなすか：

同一AggKeyであっても、history上で隣接している（連続している）範囲だけを1つの集約グループとみなします。 間に別のAggKeyを持つAura SPA通信が1件でも挟まると、そこでグループが区切られます。

これは、同じテスト手続きを時間を空けて何度も繰り返すと同一AggKeyが再度出現するため、隣接性の条件を入れないと「1回目のテスト」と「2回目のテスト」が誤って同じ集約グループに混ざってしまうためです。フォーム入力テストを1回実施した後、別の画面を操作してから同じフォームを再度テストした場合、1回目と2回目は別々の集約グループとして扱われます（間に他の通信を挟まず連続してAura通信を繰り返した場合のみ、1つのグループになります）。

9. Aura診断 タブ（能動送信・要認可）

本タブは、これまでの全タブと異なり、実際に対象ホストへHTTPリクエストを送信します。 認可された脆弱性診断対象に対してのみ使用してください。 未認可のホストに対して実行すると、不正アクセス行為に該当するおそれがあります。 他のタブ（ルール/コックピット/解析/採番/集約色）は引き続き完全に受動的です。

Google/Mandiant aura-inspector と、その解説記事 Auditing Salesforce Aura Data Exposure で説明されているSalesforce Aura診断手法を、Burp上で直接実行できるようにしたタブです。 aura-inspectorの一般公開版が意図的に実装していない実際のレコードデータ抽出まで含めて 実装しています（本ツールは正規の認可された脆弱性診断案件でのみ使用される前提のため）。

9.1 ① ターゲット設定

診断対象（ホスト・Auraセッション情報）を設定します。2つの方法があります。

1推奨: 捕捉済みパケットから設定。 Proxy history上で実際のAuraリクエストを右クリック → 「SF Helper: このパケットをAura診断対象に設定」（[解析更新]の実行有無に関わらず使えます）。または、タブ内の「候補パケット」ドロップダウン（[解析更新]済みのAura SPA通信から選択）→[選択パケットから読込]。どちらも、選択したパケットの生リクエストからその場で有効な aura.context/aura.token を直接読み取って使うため、fwuidの再発見（HTMLスクレイピング）が不要です。
2コールドスタート用（未キャプチャのゲスト対象を診断する場合など）。Base URL・Auraエンドポイントパス・Appパス・aura.context・aura.token・Cookieを手入力し、[適用]。[Auraエンドポイント自動検出] ボタンで、4つの既知パス（/s/sfsites/aura 等）へダミーリクエストを送り、有効なパスを自動判定できます。
この方式では fwuid 等のHTML自動発見（スクレイピング）は行いません。未キャプチャの対象を診断したい場合は、先にBurp経由で一度サイトを閲覧してAuraリクエストを1件捕捉してから、①の「捕捉済みパケットから設定」を使うことを推奨します。

設定した対象は、常時表示される「現在の対象」ラベル（背景色付き）で確認できます。ラベルにはホストに加えて「認証あり(Cookie送信)」／「ゲスト(Cookie未送信)」の現在のモードも表示されます。

ゲスト化（認証済みユーザーのパケットを未認証として実行する）： 認証済みユーザーのパケットを対象に設定した場合でも、そのユーザーとしてのアクセス範囲だけでなく、同じ操作をゲスト（未認証）で行うとどうなるかを確認したいことがあります。Salesforceの実際のユーザー認証はCookie（セッションID）が担っており、aura.tokenはAuraフレームワーク側の検証トークンに過ぎません。そのため[ゲスト化（Cookieを外す）]ボタンを押すだけで、Cookieを送信対象から外しaura.tokenを既定値(undefined)にリセットし、以降の②③を未認証として実行できます。ゲストブラウザで別途Auraリクエストを再捕捉する必要がありません。この操作は不可逆（元の認証済みCookieには戻せません）のため、認証済みユーザーとしての結果も確認したい場合は、先にそちらを実施してから最後にゲスト化してください。
アクティブ送信を有効にするチェックを入れるまで、②③のボタンはすべて無効化されています。本ツールが初めて能動送信を行う機能であるための安全策です。

9.3 ③ データ抽出

aura-inspector公開版が意図的に実装していない、実際のレコードデータ抽出です。

1②の結果から、抽出対象オブジェクトを選択します。選択欄は②偵察の結果（KeyPrefix・件数・一覧UI検出・備考）をそのまま表示する表になっており、件数等を見てどのオブジェクトから抽出すべきかをその場で判断できます（複数選択可、[全選択] も利用可）
21オブジェクトあたりの取得上限（既定5000件）とリクエスト間隔（既定200ms）で、どこまで収集するかを調整できます
3[抽出実行] を押すと、対象ホスト・対象オブジェクト・推定リクエスト数を示す確認ダイアログが表示されます（初期フォーカスは「キャンセル」）。内容を確認し、認可された対象であることを必ず確認したうえで「実行する」を選んでください

5進捗は表にリアルタイム表示され、[CSV出力...]（ObjectApiName, RecordId, FieldName, FieldValue のtall/long形式1ファイル）または[JSON出力...]（{オブジェクト名: [レコード, ...], ...}）でファイルに保存できます

セッション/トークンが切れたと判断した場合（HTTPステータス異常や認証エラーらしき応答）は、その時点で抽出を打ち切ります。それまでの部分結果は破棄せず、進捗表・エクスポートの両方に残ります。再開する場合は、①でパケットを再キャプチャして対象を設定し直してください。

10. 各パケットの専用タブ「SF Vuln/Agg」

Proxy history でパケットを選択すると、リクエスト/レスポンスのビューアに "SF Vuln/Agg" という専用サブタブが表示されます（Auraらしき通信、またはワードリストにヒットする通信でのみ表示）。

  • 分類（画面／画面更新(SPA)／API／静的）
  • Method / Path
  • Aura Descriptors / Aura Objects（該当する場合）
  • AggKey
  • AggRole（[解析]タブで事前に[解析更新]していれば「代表」「集約対象(代表No.X)」「単独」を表示）
  • ワード照合ヒット（Vuln-Noと、どのワードがどこ（パス/ヘッダ/ボディ、リクエスト側・レスポンス側いずれも）で見つかったか）
LWC(Lightning Web Components)の検出について： descriptorに ApexActionController/execute（汎用Apexディスパッチコントローラ）が含まれる場合、「LWCからのimperative/wire Apex呼び出しの可能性があります」という注記が表示されます。Aura Componentsのコントローラは通常 java://<Class>/ACTION$<method> の形でクラス名がdescriptorに直接現れますが、LWCは呼び出し先クラス名をparams側に載せてこの汎用コントローラを呼ぶため、descriptorだけでは判別しにくい違いがあります（あくまで推定であり断定はできません）。なお、LWCが従来のAuraホスト環境（Experience Cloud/Lightning Experience）上で動いている場合は通信自体が/sfsites/auraを通るため、本ツールの解析・Aura診断とも通常通り機能します。Salesforceの新しいサイト実行基盤であるLWR(Lightning Web Runtime)サイトはAuraを経由しないため、本ツールの検出対象外です。

11. burp_to_csv.py との使い分け

12. 技術的な注記

12.1 なぜ Python 2 / Jython なのか

Burp Suite Pro の拡張機構（Extender API）は、Java拡張のほか Jython（Python 2.7互換） と Ruby(JRuby) をサポートしていますが、CPython 3 の拡張は直接サポートされていません。 そのため python/burp_to_csv.py（CPython 3）をそのまま import することはできず、本プラグインは同一アルゴリズムを Jython 向けに再実装しています。

12.2 挙動の一致（パリティ）について

本ファイルは、Burp/Java依存の import を try/except で分離する設計になっており（ON_JYTHON フラグ）、分類・Aura集約キー計算・ワード照合ロジックの部分はBurp環境が無くても Python 3 で直接 import して動作します。この性質を利用し、python/sample_burp_packets.xml を対象に、本プラグインのロジックと burp_to_csv.py の実際の出力を突き合わせるパリティ検証を実施し、全19パケットで 分類／AggKey／AggRole／Vuln-No が完全一致することを確認済みです。

さらに、以下の合成テストでも両ファイルが同一の結果を返すことを確認済みです。

  • 同一AggKeyの通信を離れた位置に配置（間に別のAura SPA通信を挟む）→ 離れた側は別グループ／単独になる
  • descriptorを持たない同一内容（auraCmpDef等）のAura SPA通信を隣接配置 → 集約対象になる
  • 同じくdescriptorを持たないが内容（パラメータの値）が異なるAura SPA通信を隣接配置 → 集約対象にならず単独のまま
  • ①リクエスト用ルールの照合対象を、レスポンスにのみ存在する語で構成 → ヒットしない （burp_to_csv.pyと同じくリクエスト側のみが対象であることの確認。 burp_to_csv.py自体はレスポンス側の照合機能を持たないため、 この比較は①リクエスト用ルールに関するパリティ検証）
  • ②レスポンス用ルール（build_response_corpus_lower／ RESPONSE_LOCATION_ORDERを指定したmatch_rules）は burp_to_csv.pyに相当機能が無いため単体テストで直接検証： レスポンス本文にのみ存在する語がヒットすること、URLデコードが行われないこと （+等の文字を壊さないこと）、location_order省略時は 既存のリクエスト側呼び出しと完全に同じ結果になること（後方互換性）を確認済み
これは「共通ロジック部分」の検証であり、Burp API 呼び出し部分（GUI・IMessageEditorTab・IContextMenuFactory・Comment/Highlightの読み書き等）は実際の Burp Suite Pro 環境での動作確認ができていません（開発環境にBurp/Jython実行環境が無いため）。初回導入時は次の手順で必ず動作確認してください。

12.3 初回導入時の確認手順

  1. Extensions に Add → エラーなくロードされること（Errors タブ確認）
  2. python/word.csv を[ルール]タブ上段（① リクエスト用ルール）の [CSVロード...] → ルール表に正しく展開されること（下段の② レスポンス用ルールにも別途同じ手順で ロードできることを確認）
  3. ② レスポンス用ルール（下段）にレスポンス本文中の文字列にヒットするルールを1件ロードし、 上段とは異なるAND/OR条件を設定 → [解析更新]実行後、下段の表だけにヒット状況・ヒット数が 付き、上段には影響しないこと。同じVuln-Noを上段・下段の両方に定義した場合、[解析]タブの ワード照合一覧・"SF Vuln/Agg"タブでは1件のVuln-Noとして両方のロケーションのヒットが まとめて表示されること
  4. Aura通信（/sfsites/aura）を含むページを閲覧 → 選択パケットに "SF Vuln/Agg" タブが出現し、Descriptors/Objects/AggKeyが表示されること
  5. 同一フォームへの逐次入力等で複数のAura通信を連続して発生させる → [解析]タブで[解析更新] → 対象パケットを選択し "SF Vuln/Agg" タブで「代表」「集約対象」に判別されること
  6. 同じフォームテストを別の操作を挟んでもう一度実施する → 解析更新後、1回目と2回目が別々の集約グループになり、1つの大きなグループに混ざらないこと（隣接性の条件の確認）
  7. /cst/s/otc のようなAura以外の通信を複数回発生させる（別トークン等）→ 解析更新後、同一method+pathでも常に「単独」になり、誤って集約されないこと
  8. auraCmpDef/auraResourcesのようなdescriptorを持たないAura SPA通信（GET）を同じ内容で連続発生 → 集約対象として判別されること。内容が異なる同種の通信が隣接している場合は単独のままになること
  9. [集約対象に予約色を適用] → history上で集約対象のみ予約色になり、既存の色分けが保持されること
  10. [全history採番] → Comment欄先頭に番号 → [解析]タブで[解析更新]を再実行 → [解析結果をCommentへ追記] → 各パケットのComment末尾に [SF Agg=...] が付き、集約対象パケットには →代表[0005] のように代表の採番番号が入ること。再度押しても重複しないこと（冪等）
  11. Save items(XML) → burp_to_csv.py 実行 → packets.csv の No/Comment/AggKey/AggRole/Vul-No が本プラグインの表示と一致すること
  12. [解析]タブの種別ごとの集計：採番範囲を空欄のまま[表示を更新]→全件が分類ごとにカウントされること。範囲を入れて再度[表示を更新]→件数が絞り込まれ、未採番のパケットは対象外になること。同時に下のワード照合一覧の件数・内容も同じ範囲に絞り込まれること
  13. ワード照合一覧の[集約対象を除いて表示]（既定でON）：解析更新直後の一覧にAggRole「集約対象」の行が出ていないこと。チェックを外すと全件表示になり、種別ごとの集計のステータス行の数字も連動して切り替わること
  14. ワード照合一覧の行を1つクリック → 選択行の詳細欄（ヒットしたワードとロケーション／ルールComment）に内容が表示されること。別の行をクリックすると内容が切り替わること
  15. ワード照合一覧の列見出し（例: Vuln-No）をクリック → その列でソートされること。ソート後に行を1つクリックしても、選択行の詳細欄（ヒットしたワードとロケーション／ルールComment）が正しくその行の内容を表示すること（ソート前後で内容がずれないこと）
  16. 採番済みパケットの行をワード照合一覧でクリック → クリップボードに採番番号（例: [0005]）がコピーされ、ログにその旨が出ること。Burpの Proxy > HTTP History の検索窓に貼り付けて該当パケットに絞り込めること。未採番パケットの行では何もコピーされないこと
  17. [Burp Target Scope 内のみを解析対象にする]（既定でON）：Scope未設定のまま[解析更新]すると結果が0件になり、ログにヒントが出ること（意図した挙動）。Scopeを設定した状態で実行すると、Scope外の通信が集計・一覧から消え、ログに「Scope外 N 件を除外」と出ること
  18. コックピットタブ → [▶ Auto実行] を押す → まずルールインポート状況の確認ダイアログが出ること。チェックを両方外した状態でOKすると、採番・解析更新・Commentへの追記が順番に実行されること。「追加コメント全クリア」にチェックを入れて実行した場合は、続けてもう一つ確認ダイアログが出ること
  19. [Aura診断]タブ → 「アクティブ送信を有効にする」チェックを入れるまで②③のボタンが無効化されていること。認可されたテスト環境のAuraリクエストを右クリック→「このパケットをAura診断対象に設定」→「現在の対象」ラベルにホストと「認証あり(Cookie送信)」が表示されること
  20. [Aura診断]① → 認証済みユーザーのパケットを対象に設定した状態で[ゲスト化（Cookieを外す）]を押す → ラベルが「ゲスト(Cookie未送信)」に切り替わり、以降の②③が未認証として送信されること
  21. [Aura診断]②偵察 → チェックを外した項目は実行されず（ログ・表に反映されず）、チェックした項目のみ実行されること。[偵察結果をCSV出力...]/[偵察結果をJSON出力...]の両方でファイルが保存できること
  22. [Aura診断]③データ抽出 → オブジェクトを選択せずに[抽出実行]を押すとエラーログが出て確認ダイアログが出ないこと。選択後に押すと、対象ホスト・対象オブジェクト・推定リクエスト数を含む確認ダイアログが出て、初期フォーカスが「キャンセル」であること。「実行する」を選んだ場合のみ送信が始まること。[CSV出力...]/[JSON出力...]で抽出結果が保存できること

12.4 ハイライト色について

Burpが受け付ける色は red, orange, yellow, green, cyan, blue, pink, magenta, gray です。予約色は、診断中にご自身が手動で色分けに使っていない色を選んでください。「予約色のみクリア」は、現在その色になっているセルのみを対象にするため、他の色を意図的に使い分けている場合でも安全に使えます。

14. 安全上の注意

  • [ルール]・[コックピット]・[解析]・[採番]・[集約色]の各タブは、Burpが既に保持している history のデータを注釈・表示するのみです。外部へのネットワーク通信は一切行いません。
  • [Aura診断]タブのみ例外です。 このタブは対象ホストへ実際にHTTPリクエストを送信します。送信は、①でユーザーが対象を明示的に設定し、かつ「アクティブ送信を有効にする」チェックをONにした場合にのみ発生します。②偵察・③データ抽出ともボタン操作によるオンデマンド実行で、自動的・継続的に送信し続けることはありません。③データ抽出は、実行前に対象ホスト・対象オブジェクトを示す確認ダイアログでの承認が必須です。
  • [Aura診断]タブは、認可された脆弱性診断対象に対してのみ使用してください。 未認可のホストに対して実行すると、不正アクセス行為に該当するおそれがあります。§9も必ず参照してください。
  • 採番・集約色・Commentへの追記は、すべてボタン操作によるオンデマンド実行です。自動的・継続的に動作することはありません。
  • 「追加コメント全クリア」は元に戻せない操作です。ご自身が手動で [ ] を使ったメモも区別なく削除されるため、実行前の確認ダイアログを必ず確認してください。
  • 取り扱いは、認可された診断のスコープ内（サンドボックス環境等）に限定してください。
