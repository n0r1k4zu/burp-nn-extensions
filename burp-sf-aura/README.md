# SF Aura Helper — Burp Suite Pro プラグイン

Salesforce(Aura/Experience Cloud) 診断を、Burpの **HTTP history 上で直接**支援するプラグインです。
`python/burp_to_csv.py` と**同一のロジック**（分類・Aura集約キー・ワード照合）を再実装しており、
両者の解析結果（No / AggKey / AggRole / Vuln-No）が一致するように作られています。

- 対応: **Burp Suite Pro / Community**（Jython拡張が使えるエディション）
- 言語: **Python 2 / Jython**（Burpの拡張機構の制約によるもの。詳細は「技術的な注記」参照）
- ファイル: `sf_aura_burp_helper.py`（このファイル1本で完結。追加ライブラリ不要）

---

## 機能一覧

| # | 機能 | 内容 |
|---|---|---|
| ① | **採番** | HTTP history の各パケット Comment 欄先頭に `[0001]` のような固定番号を記入。Save items(XML)出力後、`burp_to_csv.py` が出す `packets.csv` の `No`/`Comment` 列と対応付けできる。**[追加コメント全クリア]** で、本ツールが `[ ]` で書き足した部分をまとめて取り除ける |
| ② | **Aura集約判別** | 同一操作の繰り返し通信（フォーム逐次送信等）を「代表／集約対象／単独」で判別。**history上で隣接している（連続している）範囲のみを1グループとみなす**ため、同じテスト手続きを時間を空けて繰り返しても別グループとして扱われる。一覧表示に加え、**「集約対象」だけに予約色をオンデマンドで適用**できる |
| ③ | **ワード照合** | [ルール]タブは**① リクエスト用**（パス・クエリ・リクエストヘッダ・リクエストボディ）と**② レスポンス用**（レスポンスヘッダ・レスポンスボディ）の上下2段に分かれ、それぞれ独立したCSV（wordlist1／wordlist2／Vuln-No／任意でcomment）とAND/OR条件を持つ。選択中(カレント)パケットの専用タブに、ヒットしたVuln-Noと「どの単語がどこで見つかったか」を表示する |
| ④ | **非干渉** | 採番はComment欄のみ、集約色は「予約色」のオンデマンド適用/クリアのみ。**ユーザー自身の色分け作業には一切自動介入しない** |
| ⑤ | **比較容易化** | 同一アルゴリズムのため `burp_to_csv.py` の出力と突き合わせやすい。Comment欄への追記（④）を通じて、Save items(XML)経由での突き合わせができる |
| ⑥ | **Aura診断（能動送信・要認可）** | [Google/Mandiant aura-inspector](https://github.com/google/aura-inspector) 相当の偵察（オブジェクト列挙・件数取得・自己登録/GraphQL/REST確認・Home URL/Record List検出・カスタムコントローラ抽出）と、実データの抽出まで行える。**本ツールが唯一、対象ホストへ実際にHTTPリクエストを送信する機能。** 詳細は本ドキュメント後半の「Aura診断 タブ」を参照 |

## 導入方法

### 1. Jython のセットアップ
1. [jython-standalone.jar](https://www.jython.org/download) をダウンロード（バージョン 2.7.x を推奨）
2. Burp Suite → **Extender → Options → Python Environment**
3. **"Location of Jython standalone JAR file"** に、ダウンロードした jar のパスを設定

### 2. 拡張のロード
1. Burp Suite → **Extender → Extensions → Add**
2. **Extension type: Python**
3. **Extension file**: `sf_aura_burp_helper.py` を選択
4. **Next** → エラーが出ないことを確認（Errorsタブも確認）
5. ロードが成功すると、Burpのタブに **"SF Helper"** が追加されます

## 使い方

Burpの **"SF Helper"** タブの中に、さらに5つのサブタブがあります（**ルール / コックピット / 解析 /
採番 / 集約色**）。最初にどれか迷ったら、まず **コックピット** タブを開いてください。

どのサブタブを開いていても、画面下部に**「実行ログ」**という枠で囲まれたコンソール風
（暗背景＋明るい緑文字＋太字）のログ欄が常に表示されます。ボタン操作の結果・件数・
エラー等はすべてここに追記されるので、何か操作した後はまずここを見てください。

### コックピット タブ（主要操作のダッシュボード）

診断中に何度も使う操作を1画面にまとめたタブです。**「Auto実行」**の枠と**「個別操作」**の枠
（それぞれ見出し付きの囲み線＝TitledBorderで区切られています）が上下に並びます。

**Auto実行**

チェックボックス2つで事前にオプションを選び、**[▶ Auto実行]** を押すと、以下を**この順番で
自動的に**まとめて実行します。

```
(追加コメント全クリア ※チェック時のみ) → 採番 → 解析更新 →
(集約対象へ予約色を適用 ※チェック時のみ) → 解析結果をCommentへ追記
```

- **[▶ Auto実行]** を押すと、まず**ルール（ワードリスト）のインポート状況を確認する
  ダイアログ**が出ます。読み込み済みなら件数を表示、未読み込みなら「ワード照合は常に
  該当なしになります」という警告付きで表示されるので、内容を確認して実行/中断を選べます
  （Auto実行はワード照合の結果までCommentへ書き込むため、ルール未インポートのまま
  実行してしまうミスを防ぐための確認です）。
- **「実行前に追加コメント全クリアを行う」**：**既定でON**です。チェックすると、Auto実行の
  中で[追加コメント全クリア]と同じ処理（Comment内の `[ ... ]` をすべて削除）を行います。
  **元に戻せない操作**のため、チェックした状態で実行すると確認ダイアログが必ず出ます
  （チェックがONのままでも、この確認で毎回止まるため誤操作にはなりません）。
  （何度もテストし直して番号や解析マーカーが積み重なっている場合に、まっさらな状態から
  やり直したい時に使います。前回の結果を残したい場合はチェックを外してください）
- **「解析後に集約対象へ予約色を適用を行う」**：**既定でON**です。チェックすると、
  解析更新の直後に[集約対象に予約色を適用]と同じ処理を行います。予約色そのものは
  [集約色]タブで選んだ色がそのまま使われます。
- 採番の接頭辞・桁数・開始番号は[採番]タブの現在の設定を使います。各ステップは
  既存の各ボタンと**まったく同じ処理**を順番に呼び出しているだけなので、
  個別に実行した場合と結果が変わることはありません。

**個別操作**

Auto実行を使わず、1つずつ実行したい場合のショートカットです。ボタンと簡単な説明を
1行ずつ並べた表形式（グリッド）にしてあり、[採番]/[解析]/[集約色]の各タブに元々ある
同じボタンを、ここからも呼び出せます（機能はまったく同じです）。

| ボタン | 説明 |
|---|---|
| 追加コメント全クリア | Comment内の `[ ]` 部分をすべて削除します（元に戻せません） |
| 採番 | Comment先頭に通し番号（例: `[0001]`）を追記します |
| 解析更新 | Proxy history 全件を再解析し、集計・一覧を更新します |
| 解析結果をCommentへ追記 | 集約判定・ワード照合の結果をCommentへ追記します |
| 集約対象に予約色を適用 | 「集約対象」のパケットにのみ予約色を適用します |
| 予約色のみクリア | 現在「予約色」になっているパケットのハイライトだけを解除します |

### ルール タブ（ワード照合の設定）

画面は上下2段に分かれています。**① リクエスト用ルール**（上段）と**② レスポンス用ルール**
（下段）はそれぞれ完全に独立した表・ボタン群・AND/OR設定を持ちます（実行ログだけは
共有です）。上段はパス・クエリ・リクエストヘッダ・リクエストボディを、下段はレスポンス
ヘッダ・レスポンスボディを照合対象にします。同じVuln-Noを両方の表に定義することも
でき、その場合は[解析]タブ上・Commentへの追記マーカー上では1件のVuln-Noとして
（両方のヒット箇所をまとめて）表示されます。

1. 各段の **[CSVロード...]** ボタンで `word.csv`（または独自作成のCSV）を読み込みます
   （上段＝リクエスト用ルール、下段＝レスポンス用ルールとして、それぞれ個別に読み込みます）
2. 読み込んだ内容は各段の表に展開され、直接セルを編集できます
3. 編集後は各段の **[表からルール反映]** を押して確定してください（押さないと編集内容は
   使われません。上段・下段それぞれ個別に反映が必要です）
4. **結合条件** は各段の **AND / OR** ラジオボタンで切り替えます（既定 AND、上段・下段で
   独立して設定できます。例：リクエスト側はAND、レスポンス側はOR、という組み合わせも可能）

> 💡 セルを入力した直後（Tab/Enterで確定する前）に**[表からルール反映]**を押しても、
> 直前の入力が正しく反映されます。[行追加]で新規行を作ってすぐ入力→反映、という
> 使い方をしても、最後のセルの入力が抜け落ちることはありません（Swingの仕様上、
> ボタンクリックだけではセル編集が自動確定しないため、内部的に明示的な確定処理を
> 行っています）。
>
> 💡 wordlist1/wordlist2・Vuln-No・commentのいずれも、**日本語を含めて問題なく
> 使えます**。押しても画面下部の実行ログに何も反応が出ない場合は、[ルール]タブ・
> [解析]タブ以外の操作（採番・集約色等）も含めて、まず拡張の再ロードを試してください。

各段の表の5列目に **「ヒット状況」**、6列目に **「ヒット数」** 列があります。[解析]タブで
[解析更新] を実行するたびに、その回の解析結果に基づいて **「ヒットあり」** または
**「★ 未ヒット」** の目印と、そのVuln-Noにヒットしたパケット数（1パケット内で複数箇所
ヒットしても1件と数える）が自動的に付きます（解析未実施、またはCSVを読み込み直した
直後はそれぞれ `-` / `0` のまま）。**「★ 未ヒット」のルールは、一度もどのパケットにも
ヒットしていない**ことを意味します。ワードの綴りが違う・そもそも対象の通信が発生
していない等の見直しに使ってください。
（この判定は、[解析]タブの範囲指定・[集約対象を除いて表示]チェックとは無関係に、
**解析対象全体**を基準にしています。表示を絞り込んでいるだけでヒット自体はしている
ケースを「未ヒット」と誤判定しないためです。また、リクエスト用・レスポンス用の
ヒット状況／ヒット数はそれぞれのルールに対して独立に集計されます）

> 💡 **文字コードは自動判定します**（UTF-8[BOM可]を優先し、デコードできない場合のみ
> cp932[Shift_JIS系]にフォールバック）。comment列に日本語を入れたのに読み込み後に
> `ã«ã¯...` のような文字化けが出る場合は、この自動判定が入る**前のバージョン**の
> 症状です。最新版であれば、ログに「文字コード: UTF-8」等の判定結果が出ます。

#### CSVの形式（2パターン対応、comment列は任意。リクエスト用・レスポンス用とも同一形式）

**パターンA：既存 `python/word.csv` と同じ、ヘッダ付き形式（+ 任意で `comment` 列）**
```csv
Vul-No,Method,param,comment
1,QrCode/CAS_CTRL_MH024,customerNumber,認可不備の疑い。要手動確認
2,_nc_external/hoge,buster,
```
→ ヘッダのいずれかの列名に「vul」を含む列を自動検出し、それを Vuln-No 列とみなします。
　同様に列名に「comment」を含む列があれば comment 列として扱います。
　残り2列は、ファイル内での左から右の順で **wordlist1 → wordlist2** として扱われます
　（この例では `Method`列 = wordlist1、`param`列 = wordlist2）。
　**comment列が無い（3列だけの）CSVもそのまま読み込めます**（comment欄は空になります）。

**パターンB：ヘッダなし、位置指定形式（+ 任意で4列目）**
```csv
recordId/accountId,GET/POST,V-001,このパターンは要注意
reqJson/filter,POST,V-002
```
→ 1列目が **wordlist1**、2列目が **wordlist2**、3列目が **Vuln-No**、
　4列目があれば **comment** として読み込まれます（無い行はcomment欄が空になります。
　上の例の2行目のように、行ごとに列数が違っていても問題ありません）。

いずれの形式でも、**各セル内は `/` 区切りで複数ワードを指定でき、同一リスト内は常にOR判定**です。
（例: `recordId/accountId` は「recordIdまたはaccountId」の意味）。`/`区切りはワードリスト2列
（wordlist1・wordlist2）専用で、comment列は`/`区切りにせず自由記述のテキストとして扱われます。

**comment列の使いみち**：ルール表・[解析]タブのワード照合一覧の両方に、この列の内容が
そのまま表示されます（例: 「認可不備の疑い、要手動確認」のような、そのVuln-Noに対する
補足メモ）。Burp の Comment（採番・集約マーカー等）とは別物です。

#### 判定ロジック

```
(wordlist1のいずれかがヒット) [AND または OR] (wordlist2のいずれかがヒット)
```

- **AND**（既定）: `burp_to_csv.py --word-list` と同一の判定になります
- **OR**: どちらか一方のリストにヒットすれば成立する、より緩い条件（本プラグイン独自の拡張）

#### ワイルドカード（`*`）

wordlist1・wordlist2のセルに **`*`** を1語として指定すると、そのリストは**常に条件成立した
ものとして扱われ**、実際にコーパス中で `*` という文字列を探すことはしません。
片方のリストだけで判定したい場合に使います。

```csv
Vul-No,Method,param
1,*,isAdmin
```

→ wordlist1（この例では `Method`列）が `*` なので無条件成立、**`isAdmin` が見つかるかどうか
だけでVuln-No 1のヒットが決まります**。

> ⚠️ **ワイルドカードを含むルールは、AND/OR設定に関わらず、常にAND相当で判定されます。**
> 素直に「OR」のまま評価すると、ワイルドカード側が常に真になるため、`(常に真) OR (isAdminの
> 一致)` は**もう一方の条件を一切確認せずに常にヒットしてしまいます**（意図しない緩さ）。
> これを避けるため、ワイルドカードが絡むルールは、結合条件（AND/OR設定）を無視して常に
> `(常に真) AND (isAdminの一致)` として判定します。結果として、AND/OR設定を「反転」させた
> ような形になりますが、これは「ワイルドカードでない側の実際の一致結果だけでヒットを
> 判定したい」という意図を、OR設定時にも一貫して成立させるための挙動です。
> `burp_to_csv.py`側は元々AND固定のため、この反転は発生しません（ワイルドカード側が
> 常に真になるだけで、判定方式自体は変わりません）。

同一リスト内の他の語と `*` を併記した場合（例: `*/foo`）も、OR判定の性質上、`*` が1つでも
あればリスト全体が無条件成立になります（`foo`単独での判定にはなりません）。

照合範囲は、**① リクエスト用ルール（上段）＝リクエストパケットの パス・クエリ・
リクエストヘッダ（Cookie含む）・リクエストボディ**（`burp_to_csv.py`の`packet_search_text`と
同じ範囲）、**② レスポンス用ルール（下段）＝レスポンスヘッダ・レスポンスボディ**です。
レスポンスは分類（画面／画面更新(SPA)／API／静的の判定）にも引き続き使われます。

> 💡 レスポンス用ルールの照合では、リクエストボディの `message=` パラメータのような
> URLデコードは**行いません**（レスポンス本文はURLエンコードされている前提がなく、
> 誤ってデコードすると本来の `+` 等の文字を壊してしまうため）。

> 💡 **照合の実装は、Insertion Point（キー単位への分解）ではなく、リクエストボディ全体を
> 1つの文字列としたシンプルな部分文字列検索です。** JSONがどれだけネストしていても、
> キー名や値はテキスト上では連続した文字列として存在するため、階層に関係なくワードを
> 検出できます（Insertion Point解析への依存が無いため、JSONパース失敗や二重シリアライズ等の
> 影響を受けません）。ただし、Auraの `message=` パラメータはURLエンコードされたJSONのため、
> **照合前にURLデコードしてから検索**します（デコードしないと `://` や `"` のような記号を
> 含むワードが生テキスト上の `%3A` 等と一致しなくなるため）。

### 解析 タブ（一覧確認）

1. **[解析更新（HTTP history全件を再解析）]** を押すと、現在の Proxy history 全件を解析します
   （バックグラウンドで実行されるため、Burpの操作は継続できます）
   - **[Burp Target Scope 内のみを解析対象にする]** をチェックすると、Burpの
     **Target タブ → Scope** の設定（`callbacks.isInScope`）で対象URLを絞り込みます。
     **既定でON**です。**先にBurpのTarget タブでScope（Include in scope）を設定してから
     使ってください。** Scopeを何も設定していない状態のままだと、解析結果が0件になります
     （その場合はログに「全件がScope外と判定されました」というヒントが出ます）。
     Scopeを使わない場合は、このチェックを外せば従来通りhistory全件が対象になります。
     URL取得やスコープ判定自体に失敗した場合は、安全側（除外しない）に倒します。
     チェックの変更は**次回の[解析更新]から反映**されます（すでに表示されている集計・
     一覧を即座には変えません）。
     この絞り込みは解析（②③、集約色適用、Commentへの追記）にのみ適用され、
     **①採番（Comment先頭への番号付与）には影響しません**（採番は従来通りhistory全件が
     対象です。番号は`burp_to_csv.py`側のNo/Comment対応付けに使うため、Scope設定の
     有無に関わらず一貫させています）。
2. **種別ごとの集計**：分類（**画面／画面更新(SPA)／API／静的**）ごとの件数と合計を表示します。
   個々のパケットを一覧表示していた従来の「Aura集約 一覧」表は廃止し、まず全体のボリューム感を
   把握できるサマリー表示に置き換えています（個々のパケットのAggKey/AggRole/Descriptors等は、
   Proxy historyで選択した際に表示される **"SF Vuln/Agg"** タブで確認できます）。
   - **表示対象の採番範囲**を、①採番タブで振った番号（`[0001]`〜等）で絞り込めます。
     例えば「51〜100番だけ」のように、テストのある区間だけを対象にできます。
     空欄のまま **[表示を更新]** を押す（または解析更新後）と全件が対象になります。
     範囲を指定した場合、**まだ採番していないパケットは対象から除外**されます（先に採番してください）。
     - From/Toの数字は手入力のほか、**Proxy historyでパケットを右クリック**→
       **「SF Helper: [解析]表示範囲のFromにこの採番番号をセット」**／
       **「...のToにこの採番番号をセット」**でも設定できます。対象パケットのComment
       先頭にある採番番号を読み取ってそのままFrom/To欄に入力するので、「この画面から
       この画面まで」を数字を見て手入力する必要がありません。複数選択している場合は
       先頭の1件が使われます。セットすると（解析済みであれば）即座に集計・一覧が
       再フィルタされます。未採番のパケットを選んだ場合は、その旨がログに出ます。
   - **この範囲指定は、下の「ワード照合 一覧」にも同じ範囲で適用されます**（集計と一覧で
     対象がズレることはありません）。
   - **件数は「集約対象を含む」「集約対象を除く」の2列で並べて表示**します。
     「含む」は履歴上のパケットをそのまま数える件数（②Aura集約の同一操作の繰り返しも
     1件ずつ数える）、「除く」は集約対象（②で「集約対象」と判定されたパケット）を除いた件数
     （＝代表+単独のみ。同一操作の繰り返しはグループにつき1件として数えるため、実質的な
     「操作の種類の数」に近い値になります）。**画面／API／静的は集約判定の対象外
     （集約対象になり得るのは画面更新(SPA)のみ）のため、この2列は常に同じ値**になります。
   - **表の下の「表示対象: N / M パケット（...）」というステータス行の N は、下の
     「ワード照合 一覧」にある[集約対象を除いて表示]チェックの状態に連動**します。
     チェックがONなら「除く」列の値（実質的な操作の種類の数）、OFFなら「含む」列の値になり、
     チェックを切り替えると即座に数字が変わります。M（分母）は採番範囲・Scope絞り込み後の
     総パケット数で、チェックの状態に関わらず一定です。
     **ただしこのNは「パケット数」であり、下のワード照合一覧に実際に表示されている
     「行数」（＝ヒット件数。1パケットが複数のVuln-Noにヒットすれば複数行になります）とは
     単位が異なるため、一致するとは限りません。** 行数はワード照合一覧の下にある
     「ワード照合一覧: N 件表示」の方を見てください。

   一度もヒットしなかったVuln-Noの確認は、[ルール]タブの表の「ヒット状況」列（§5）で
   行います。[解析]タブ自体には未ヒットの一覧は表示しません。

#### なぜ「画面」の件数が「画面更新(SPA)」より多いのか

分類（②の「種別ごとの集計」の元になる区分）は、`classify()` 関数が次の**優先順位**で
判定しています（`burp_to_csv.py` と同一ロジック）。

1. パスに `auraAnalytic` を含む → **API**
2. パスに Aura関連のマーカー（`/aura`, `sfsites/aura`, `auraCmpDef`, `auraResources`）を含む、
   またはボディに `message=`/`aura.context=` を含む → **画面更新(SPA)**
3. 拡張子/レスポンスMIMEが静的アセット相当（js/css/画像/フォント等） → **静的**
4. レスポンスMIMEが `html` を含む → **画面**
5. どれにも該当しない → **API**

つまり「**画面**」は、Auraの操作（SPA通信）でも静的アセットでもない、**HTMLを返すリクエスト
すべて**が該当する分類です。ページ遷移・リロード・別画面への移動は、実際にAuraのアクションを
何も呼ばなくても1回ごとに1件の「画面」として計上されます。一方「画面更新(SPA)」は、**実際に
フォーム入力やボタン操作などでAuraアクションが呼ばれた通信**だけが該当します。

そのため、サイトを一通り巡回・閲覧しただけで、個々のフォームやコンポーネントを深く操作
（入力・送信・一覧の絞り込み等）していない場合は、「画面」（ページ遷移の数）が
「画面更新(SPA)」（実際に操作した回数）を上回るのが自然です。逆に、同じフォームへの
入力操作を繰り返すテストを行った場合は、「画面更新(SPA)」（含む）の件数が跳ね上がりますが、
これは主に②の集約対象（同一操作の繰り返し）によるものなので、「除く」列（実質的な操作の
種類の数）と見比べると実態がつかみやすくなります。
3. **ワード照合 一覧**：**Comment / AggRole / Method / URL / 分類 / Vuln-No / ヒット元 /
   ヒットしたワードとロケーション / ルールComment** を表示
   - **ヒット元**列は、そのVuln-Noが[ルール]タブの**①リクエスト用ルール**／**②レスポンス用
     ルール**のどちらでヒットしたかを表示します（`リクエスト` / `レスポンス` / 両方の表に
     同じVuln-Noを定義していて両方でヒットした場合は `リクエスト+レスポンス`）
   - **各列見出しをクリックするとその列でソートできます**（もう一度クリックで昇順/降順切替）。
     例えばVuln-No列でソートして同じ脆弱性のヒットをまとめて確認する、といった使い方ができます。
     **Vuln-No列は文字列の辞書順（1,10,3のような順）ではなく、数値としての自然順
     （1,3,10）でソートされます**（`SEC-1`のような数値以外を含む値が混在していても、
     数値部分だけを数値として比較するため破綻しません）。
   - 上の「種別ごとの集計」と**同じ採番範囲の絞り込み**が適用されます。
   - **AggRole**列は**Comment列のすぐ次**に配置しています。そのパケットが
     「代表／集約対象／単独」のいずれかが一覧上ですぐわかります（集約対象かどうかを
     確認するために、いちいち選択パケットの専用タブを開く必要がありません）。
   - **Method / URL**列で、どの通信がヒットしたのかを一覧上で直接確認できます
     （Burpの履歴を見比べに行かなくても、この一覧だけで通信の内容がある程度わかります。
     URLにHost部分も含まれるため、Host専用の列は設けていません）。
   - **分類**列で、そのパケットが「画面／画面更新(SPA)／API／静的」のどれかが一覧上でわかります
     （上の「種別ごとの集計」と同じ表記です）。
   - 見出しの横にある **[集約対象を除いて表示]** チェックボックスで、AggRole が「集約対象」の
     行を一覧から非表示にできます。**既定でON**です（同一操作を繰り返しテストした場合、
     集約対象の行は代表と同じ内容がそのまま並ぶだけのことが多く一覧が埋もれがちなため、
     まず代表・単独だけの実質的な一覧を見せる運用にしています）。集約対象も含めて全件
     確認したい場合はチェックを外してください。チェックの変更は（解析済みであれば）
     押した瞬間に反映されます（[表示を更新]を押す必要はありません）。表の下に、
     表示件数と非表示にした件数が出ます。
   - 「ヒットしたワードとロケーション」は `語@場所`（例: `customerNumber@reqBody`）の形式で、
     Commentに追記されるマーカーの `Vuln=` 部分と同じ表記です。
   - **ルールComment**列には、`word.csv` の `comment` 列（あれば）の内容がそのまま表示されます
     （例: 「認可不備の疑い、要手動確認」等、そのVuln-Noに対する補足メモ）。同じVuln-Noの
     ルールが複数ある場合は、最後に読み込まれたものが表示されます。comment列が無いCSVの
     場合は空欄になります。
   - **表の下に「選択行: ヒットしたワードとロケーション」「選択行: ルールComment」という
     2つの表示欄**があります。表の行を1つクリックすると、その行の内容がそれぞれの欄に
     表示されます。行の選択を外すと欄は空になります。
     - **「選択行: ヒットしたワードとロケーション」欄は、`ロケーション → ヒットしたワード`
       の順の2列を持つ小さな表**で、ヒットしたワード1件につき1行で表示します
       （1行のテキストに詰め込まず、ヒット件数分の行が並びます）。
     - **「選択行: ルールComment」欄**は、長文でも折り返して表示するテキストボックスです。
       テーブルのセルはいちいち列幅を広げないと長い文章が見切れてしまいますが、この欄は
       折り返されるだけで文章が切れることはなく、スクロールも可能です。
   - **行を選択すると、その行のComment先頭にある採番番号（例: `[0005]`）が自動的に
     クリップボードにコピーされます。** BurpのAPIには拡張からHistoryタブの検索窓へ直接
     値をセットしたり、該当行を選択・スクロールしたりする手段が存在しないため、コピー＆
     手動貼り付けで代替しています。コピー後、Burpの **Proxy > HTTP History** タブに切り替えて
     検索窓（虫眼鏡アイコン）に貼り付ければ、該当パケットをすぐに絞り込めます。採番されていない
     パケットの行を選択した場合は何もコピーされません。

> 💡 ワード照合一覧の先頭列は **Comment**（内部の通し番号Noではなく）です。Noは実行のたびに
> 変わり得るため画面表示には使わず、実際に history 上で目に見える Comment 欄で
> パケットを判別できるようにしています。まだ何もメモが無いパケットはComment列が空欄になります。

#### ワード照合一覧のCSV出力

見出しの **[この一覧をCSV出力...]** ボタンを押すと、その時点で一覧に**表示されている行**
（採番範囲の絞り込み・[集約対象を除いて表示]チェックの状態がそのまま反映されます）を
CSVファイルに保存します。保存先は都度ダイアログで選択します。

出力される列は次の通りです。

**Comment / AggRole / Method / URL / 分類 / Vuln-No / ヒット元 / ヒットしたワード@ロケーション /
ルールComment / Request / Response**

先頭8列は画面のワード照合一覧と同じ内容です（**「ヒット元」列**でそのVuln-Noが①リクエスト用
ルール／②レスポンス用ルールのどちらでヒットしたかがわかります）。加えて、該当パケットの **Request** と
**Response**（生のリクエスト/レスポンス全体）を列として追加します。

**Comment列**は、Burp上のComment欄の内容から、本ツールが末尾に追記する解析マーカー
（`[SF Cls=... Vuln(N件): ...]` 等。上記「解析結果をCommentへ追記」で書き込まれる部分）
を取り除いたものを表示します。**①採番の番号（例 `[0005]`）とユーザーが手で書いた
コメントまで**が対象で、本ツールが自動追記した部分は含みません。

Excelでの閲覧を想定し、Request/Responseは次のように整形されます。

- 改行（`\r\n` `\n` `\r`）はすべて半角スペースに置換し、1パケット=1行に収めます。
- 長さが500文字を超える場合は先頭500文字で切り詰め、`<---snip--->`という目印と
  `(全N文字)`という元の文字数を末尾に付記します（省略されたことが一見してわかるように
  するためで、省略された内容自体はCSVには含まれません。全文が必要な場合はBurp上で
  該当パケットを直接確認してください）。
- 文字コードはUTF-8（BOM付き）で保存するため、Excelでそのまま開いても文字化けしません。

ヒットが無いパケットは出力対象外です（画面の一覧と同じく、Vuln-Noにヒットした行のみが
対象になります）。1パケットが複数のVuln-Noにヒットしている場合は、画面表示と同様に
Vuln-Noの数だけ行が分かれます。

#### 解析結果をCommentへ追記（集約判定＋ワード照合）

**[解析結果をCommentへ追記（集約判定＋ワード照合）]** ボタンを押すと、解析済みの
**全パケット**の Comment 欄の末尾に、次の形式で情報を追記します。

```
[SF Cls=画面更新(SPA) Agg=集約対象(size=3)→代表[0005] Vuln(1件):
・1(customerNumber@reqBody,QrCode@path)[要手動確認]]
[SF Cls=画面更新(SPA) Agg=代表(size=3)]
[SF Cls=API Agg=単独 Vuln(2件):
・1(customerNumber@reqBody)[要手動確認]
・3(hoge@reqBody)]
```

- **Cls=** の部分は必ず書き込まれます（**画面／画面更新(SPA)／API／静的** の4分類のいずれか）。
  値の表記は `burp_to_csv.py` が出力する `packets.csv` の「分類」列と**完全に同じ表記**にしてあります
  （独自の言い回しにすると、Comment上の表記とCSVの分類列を見比べる際に紐づけにくくなるため）。
  Burpの Comments 列を見るだけで、パケットの通信種別を判別できます。
- **Agg=** の部分は必ず書き込まれます（**代表 / 集約対象(グループ件数) / 単独** のいずれか）。
  これにより、ワード照合のヒットが無いパケットも含め、**「集約対象かどうか」を
  Burpの Comments 列を見るだけで判別**できます。
- **集約対象**の場合、代表パケットの**現在のComment先頭にある採番番号**（①採番タブが書く
  `[0005]` 等）を読み取り、**`→代表[0005]`** として、どの代表に集約されたのかを
  番号で参照できるようにします。**先に[採番]タブで採番してから**このボタンを押すと
  番号が入ります。まだ代表が採番されていない場合は `→代表(未採番)` と表示されます。
- **Vuln(N件):** の部分は、ワードリストにヒットしたパケットにのみ付きます（ヒットが無ければ省略）。
  **ヒット件数が1件でも複数件でも、常にこの見出し＋改行形式で統一しています**
  （1件だけの場合と複数件の場合で書き方が異なると見た目で気付きにくいため）。
  1件ずつ改行し、行頭に `・` を付けて `Vuln-No(語@場所, 語@場所, ...)[ルールComment]` の
  形式で列挙します。**①見つかったVuln-No** と、**②実際にヒットした単語そのものと、
  それが見つかった場所**（`reqBody`=リクエストボディ、`path`=パス、`query`=クエリ、
  `reqHeaders`=リクエストヘッダ。**照合はリクエストパケットのみが対象で、レスポンスは
  対象外**です）の両方がComment上だけで確認できます。**さらに、そのVuln-Noに対応する
  ルールに `word.csv` の comment 列が設定されていれば、末尾に `[...]` で追記されます**
  （例: `・1(customerNumber@reqBody)[要手動確認]`）。comment列が無い、または空欄の
  ルールの場合はこの部分は付きません（ワード照合一覧の「ルールComment」列と同じ内容・
  同じ優先順位です。§6.3参照）。
- 既存のメモ内容は保持され、**末尾に追記**されます（採番①はComment**先頭**を使うため衝突しません）。
- 何度実行しても、前回このボタンが書いたマーカー（旧バージョンの `[Vuln: ...]` 形式も含む）を
  検出して置き換えるため、**重複追記されません**（冪等）。

**推奨手順**：①[解析更新] → ②[採番]タブで[全history採番] → ③再度[解析更新]
→ ④[解析結果をCommentへ追記]。この順で行うと、代表の番号が確実に反映されます
（②の前に④を押した場合でも、代表パケットの"現在の"Commentを都度参照するため、
②の後に④だけ再度押せば番号が入ります）。

> ⚠️ 解析は「実行した時点」の history 順序に基づきます。後からトラフィックが増えると
> グループの内容（size等）が変わることがあるため、**採番・集約色適用・Comment追記の直前に
> 必ず[解析更新]を再実行**してください。

### 採番 タブ

- **接頭辞・桁数・開始番号** を指定し、**[全history採番]** を押すと、Comment欄の先頭に
  `[0001] ` のような番号が追加されます（既存のメモ内容は保持されます）。
- 既に採番済み（同じ接頭辞のパターンで始まる）パケットはスキップされます（再実行しても安全）。
- **[採番解除（全history）]** で、先頭の番号部分だけを取り除きます（メモ本文は残ります）。
- **右クリックメニュー**（Proxy historyなどで対象を選択→右クリック）からも
  **「SF Helper: 選択パケットに採番」** で、選択したパケットだけに採番できます。
- **[追加コメント全クリア（[ ]を全削除）]** で、Comment内の `[ ... ]` 形式の部分を
  **すべて**（先頭の採番トークン・末尾の解析マーカー・入れ子になったもの、いずれも）
  まとめて取り除きます。本ツールは書き込みを常に `[ ]` で囲む設計にしているため、
  逆に「`[ ]` で囲まれたものを消せば、本ツールが追記した分だけをまとめて取り除ける」
  という考え方です。**ご自身が手動で `[ ]` を使ったメモも区別なく削除される**ため、
  実行前に確認ダイアログが出ます（元に戻せません）。

**運用のコツ**：番号は「実行時点のhistory順」で決まります。トラフィック取得が完了してから、
**Save items でXML出力する直前**に採番することを推奨します。これにより、番号と
`burp_to_csv.py` が出力する `No` 列がズレなく対応します。

### 集約色 タブ

Auraのフォーム逐次通信のように、**同じ操作が何度も繰り返されている通信**を見分けるための機能です。

1. **予約色** を選択します（**ご自身の色分け作業では使っていない色**を選んでください。既定は `gray`）
2. **[集約対象に予約色を適用（オンデマンド）]** を押すと、[解析]タブで判定済みの
   「集約対象」（＝代表以外の重複通信）にだけ、選択した予約色が適用されます
3. **[予約色のみクリア]** を押すと、**現在その予約色になっているパケットの色だけ**を解除します
   （ご自身が付けた他の色、例えば「赤=重大」等には一切触れません）

- どちらのボタンも、**押した時だけ**動作します。自動的・継続的に色を変更することはありません。
- 適用前に、必ず [解析] タブで **[解析更新]** を実行しておいてください。

> 💡 「集約対象」の考え方は `burp_to_csv.py` と同一です。同一のAuraアクション・対象オブジェクト・
> 呼び出し元画面・認証状態から成る通信グループのうち、最初の1件（=代表）以外を「集約対象」と
> 判定します。詳しくは `python/burp_to_csv_マニュアル.html` の該当セクションを参照してください。
>
> ⚠️ **集約対象になり得るのは Aura の SPA通信（画面更新(SPA)）だけです。** それ以外の通信
> （画面/API/静的。例: `/cst/s/otc` のようなワンタイムトークンを含むリクエスト等）は、
> method+pathだけの粗いキーになり無関係な別リクエスト同士を誤って同一グループに丸めて
> しまうリスクがあるため、**常に「単独」**として扱われます。
>
> 💡 Aura SPA通信のうち、**Aura descriptorを持つもの**（`RecordUiController/...`等の具体的な
> アクション呼び出し）は、アクション・対象オブジェクト・呼び出し元画面・認証状態から成る
> キーで識別します。**descriptorを持たないもの**（`auraCmpDef`/`auraResources`等の
> コンポーネント定義取得のようなGETリクエスト）も集約対象に含まれますが、この場合は
> **パラメータの値まで含めて**内容が完全に一致する場合のみ同一グループとみなします
> （名前だけが同じでも、値＝実際に読み込んでいる内容が違えば別グループのままです）。
>
> ⚠️ **同一AggKeyであっても、history上で隣接している（連続している）範囲だけを
> 1つの集約グループとみなします。** 間に別のAggKeyを持つAura SPA通信が1件でも挟まると、
> そこでグループが区切られます。これは、**同じテスト手続きを時間を空けて何度も繰り返すと
> 同一AggKeyが再度出現する**ため、隣接性の条件を入れないと「1回目のテスト」と「2回目のテスト」
> が誤って同じ集約グループに混ざってしまうためです。例えば、フォーム入力テストを1回実施した後、
> 別の画面を操作してから同じフォームを再度テストした場合、1回目と2回目は**別々の集約グループ**
> として扱われます（間に他の通信を挟まず連続してAura通信を繰り返した場合のみ、1つのグループに
> なります）。

#### 色情報スナップショット（バックアップ / リストア）

[集約色]タブの**下半分**に、**Historyの色分け状態そのものを丸ごとバックアップ・リストアできる機能**が
あります。予約色の適用/クリアとは独立していて、ユーザー自身が手動で付けた色も含めて対象になります。

1. **[現在の色情報をスナップショット...]** を押すと、コメント入力ダイアログが出ます（空欄でも可）。
   OKを押すと、その時点でHistoryに存在する**全パケットの色（無色も含む）**が1件のスナップショットとして
   記録されます
2. 履歴は表（No / 日時 / コメント / 色あり件数の全件数）に一覧表示され、何度でも取得できます
3. 表からスナップショットを1件選択し、**[選択したスナップショットをリストア]** を押すと、
   そのスナップショット取得時点に存在したパケットの色が、当時の状態（無色だったパケットは無色に戻る）に
   一括で上書きされます。**スナップショット取得後に増えた通信には触れません**
4. 不要になったスナップショットは、選択して **[選択したスナップショットを削除]** で履歴から削除できます
5. 選択に関係なく、**[全パケットの色を一括クリア]** を押すと、Historyの全パケットの色を現在の色に
   関わらず一括で無色に戻せます

> ⚠️ リストア・一括クリアはどちらも元に戻せない操作です。現在の色分け状態を失いたくない場合は、
> 実行の前に現在の状態もスナップショットしておいてください。
>
> 💡 スナップショットは拡張の実行中のみメモリ上に保持されます（ファイルへの保存は行いません）。
> Burpの拡張をアンロード/リロードすると、それまでのスナップショット履歴は失われます。

### Aura診断 タブ（能動送信）

> ⚠️ **本タブは、これまでの全タブと異なり、実際に対象ホストへHTTPリクエストを送信します。**
> **認可された脆弱性診断対象に対してのみ使用してください。** 未認可のホストに対して実行すると、
> 不正アクセス行為に該当するおそれがあります。他のタブ（ルール/コックピット/解析/採番/集約色）は
> 引き続き完全に受動的（Burpが既に保持しているhistoryの注釈・表示のみ）です。

[Google/Mandiant aura-inspector](https://github.com/google/aura-inspector) と、その解説記事
[Auditing Salesforce Aura Data Exposure](https://cloud.google.com/blog/ja/topics/threat-intelligence/auditing-salesforce-aura-data-exposure)
で説明されているSalesforce Aura診断手法を、Burp上で直接実行できるようにしたタブです。
aura-inspectorの一般公開版が意図的に実装していない**実際のレコードデータ抽出**まで含めて
実装しています（本ツールは正規の認可された脆弱性診断案件でのみ使用される前提のため）。

#### ① ターゲット設定

診断対象（ホスト・Auraセッション情報）を設定します。2つの方法があります。

- **推奨: 捕捉済みパケットから設定**
  - Proxy history上で実際のAuraリクエストを**右クリック** →
    **「SF Helper: このパケットをAura診断対象に設定」**（[解析更新]の実行有無に関わらず使えます）
  - または、Aura診断タブ内の「候補パケット」ドロップダウン（[解析更新]済みのAura SPA通信から
    選択）→ **[選択パケットから読込]**
  - どちらも、選択したパケットの生リクエストから **その場で有効な** `aura.context`/`aura.token`
    を直接読み取って使うため、fwuidの再発見（HTMLスクレイピング）が不要です。
- **コールドスタート用（未キャプチャのゲスト対象を診断する場合など）**: Base URL・Auraエンドポイント
  パス・Appパス・`aura.context`・`aura.token`・Cookieを手入力し、**[適用]**。
  **[Auraエンドポイント自動検出]** ボタンで、4つの既知パス（`/s/sfsites/aura` 等）へダミー
  リクエストを送り、有効なパスを自動判定できます。
  - **この方式ではfwuid等のHTML自動発見（スクレイピング）は行いません。** 未キャプチャの対象を
    診断したい場合は、先にBurp経由で一度サイトを閲覧してAuraリクエストを1件捕捉してから、
    上記の「捕捉済みパケットから設定」を使うことを推奨します。

設定した対象は、常時表示される **「現在の対象」ラベル**（背景色付き）で確認できます。ラベルには
ホストに加えて **「認証あり(Cookie送信)」／「ゲスト(Cookie未送信)」** の現在のモードも表示されます。

##### ゲスト化（認証済みユーザーのパケットを未認証として実行する）

**認証済みユーザーのパケットを対象に設定した場合でも、そのユーザーとしてどこまでアクセスできるか
だけでなく、同じ操作をゲスト（未認証）で行うとどうなるかも確認したいことがあります。** その場合は
**[ゲスト化（Cookieを外す）]** ボタンを押してください。

- Salesforceの実際のユーザー認証は **Cookie（セッションID）** が担っており、`aura.token` は
  Auraフレームワーク側の検証トークンに過ぎません。そのため、対象に設定済みのセッションから
  **Cookieを送信対象から外し、`aura.token` を既定値(`undefined`)にリセットするだけ**で、
  以降の②偵察・③データ抽出を未認証（ゲスト）として実行できます。
- これにより、わざわざゲストブラウザで別途Auraリクエストを再捕捉しなくても、認証済みユーザーの
  パケット1件から「そのユーザーとしてのアクセス範囲」と「ゲストとしてのアクセス範囲」の両方を
  同じ手順（①→②→③）で確認できます。
- ゲスト化は不可逆な操作です（元の認証済みCookieには戻せません）。認証済みユーザーとしての
  結果も確認したい場合は、先にそちらを実施してから最後にゲスト化してください。

#### アクティブ送信の有効化（安全ガード）

タブ最上部の **「アクティブ送信を有効にする」** チェックを入れるまで、②③のボタンはすべて
無効化されています。これは本ツールが初めて能動送信を行う機能であるための安全策です。

#### ② 偵察

チェックボックスで、**どこまで調査するかを調整**できます（既定は全項目ON）。

| 項目 | 内容 |
|---|---|
| オブジェクト一覧取得 | `HostConfigController/getConfigData` でSalesforceオブジェクトAPI名・KeyPrefixを列挙（1リクエスト） |
| 各オブジェクトの件数取得 | オブジェクトごとの総レコード数を取得（オブジェクト数に応じたリクエストが発生） |
| Record List UI検出 | 一覧表示コンポーネントでレコードが見えるオブジェクトを検出（同上） |
| Home URL検出 | 未認可アクセスの可能性がある管理系URLを検出 |
| 自己登録確認 | ゲストからのアカウント自己登録が有効か確認 |
| GraphQL可用性確認 | データ抽出で優先的に使うGraphQL（`uiapi`）が使えるか確認 |
| カスタムコントローラ抽出 | アプリページとリソースJSを取得し、通常の閲覧では呼ばれないカスタムApexコントローラ参照を検出 |

「件数取得」「UI検出」のみチェックした場合も、内部的にオブジェクト一覧取得を併せて実行します。

結果は4つの表（オブジェクト一覧／ホームURL一覧／カスタムコントローラ一覧／その他チェック結果）に
表示され、**[偵察結果をCSV出力...]**（区分列を持つ1ファイルのtall形式。Excelでの一覧確認向け）
または **[偵察結果をJSON出力...]**（4種の結果をそのまま構造化して保持）でファイルに保存できます。

#### ③ データ抽出

**aura-inspector公開版が意図的に実装していない、実際のレコードデータ抽出です。**

1. ②の結果から、抽出対象オブジェクトを選択します。選択欄は②偵察の結果（KeyPrefix・件数・
   一覧UI検出・備考）をそのまま表示する表になっており、**件数等を見てどのオブジェクトから
   抽出すべきかをその場で判断できます**（複数選択可、**[全選択]** も利用可）
2. **1オブジェクトあたりの取得上限**（既定5000件）と**リクエスト間隔**（既定200ms）で、
   **どこまで収集するかを調整**できます
3. **[抽出実行]** を押すと、対象ホスト・対象オブジェクト・推定リクエスト数を示す**確認ダイアログ**
   が表示されます（初期フォーカスは「キャンセル」）。内容を確認し、認可された対象であることを
   必ず確認したうえで「実行する」を選んでください
4. GraphQL（`uiapi`）が利用可能な場合はそちらを優先します（Salesforceの2,000件ページ上限を
   回避できるため）。利用不可の場合は `getItems`（`layoutType=FULL`）にフォールバックします。
   `getItems`側は2,000件のページ上限があり、到達した場合は `sortBy=Name`/`-Name` での
   再取得を試みますが、**完全性は保証されません**（結果に「不完全な可能性あり」と表示されます）
5. 進捗は表にリアルタイム表示され、**[CSV出力...]**（`ObjectApiName, RecordId, FieldName,
   FieldValue` のtall/long形式1ファイル）または **[JSON出力...]**
   （`{オブジェクト名: [レコード, ...], ...}`）でファイルに保存できます

> 💡 ②偵察の「オブジェクト一覧」表、③データ抽出の対象選択表・進捗表とも、**「件数」列は
> 列見出しをクリックすると数値としてソートできます**（未取得の行は末尾に並びます）。
> 「まず件数が多いオブジェクトから確認する」といった優先順位付けに使えます。

セッション/トークンが切れたと判断した場合（HTTPステータス異常や認証エラーらしき応答）は、
その時点で抽出を打ち切ります。**それまでの部分結果は破棄せず**、進捗表・エクスポートの両方に
残ります。再開する場合は、①でパケットを再キャプチャして対象を設定し直してください。

## 各パケットの専用タブ「SF Vuln/Agg」

Proxy history でパケットを選択すると、リクエスト/レスポンスのビューアに **"SF Vuln/Agg"** という
専用サブタブが表示されます（Auraらしき通信、またはワードリストにヒットする通信でのみ表示）。

表示内容：
- 分類（画面／画面更新(SPA)／API／静的）
- Method / Path
- Aura Descriptors / Aura Objects（該当する場合）
  - descriptorに`ApexActionController/execute`（汎用Apexディスパッチコントローラ）が含まれる場合、
    **「LWC(Lightning Web Components)からのimperative/wire Apex呼び出しの可能性があります」**
    という注記が表示されます。Aura Componentsのコントローラは通常`java://<Class>/ACTION$<method>`
    の形でクラス名がdescriptorに直接現れますが、LWCは呼び出し先クラス名をparams側に載せてこの
    汎用コントローラを呼ぶため、descriptorだけでは判別しにくい違いがあります（あくまで推定であり
    断定はできません）
- AggKey
- **AggRole**（[解析]タブで事前に[解析更新]していれば「代表」「集約対象(代表No.X)」「単独」を表示）
- **ワード照合ヒット**（Vuln-Noと、どのワードがどこ（パス/ヘッダ/ボディ、リクエスト側・
  レスポンス側いずれも）で見つかったか）

## `burp_to_csv.py` との使い分け・比較の考え方

| | burp_to_csv.py | 本プラグイン |
|---|---|---|
| 動作場所 | CLI（XMLを後処理） | Burp上でリアルタイム |
| 用途 | 網羅的な一括レポート出力（triage.md等） | 診断作業中のその場確認・注釈付け |

4. `packets.csv` の `Comment` 列（プラグインが書き込んだ `[0005] ... [SF Agg=... Vuln=...]` を含む）
   を見れば、Burp上で確認した内容とXML経由の解析結果を突き合わせられる

## 技術的な注記（重要）

### なぜ Python 2 / Jython なのか
Burp Suite Pro の拡張機構（Extender API）は、Java拡張のほか **Jython（Python 2.7互換）** と
Ruby(JRuby) をサポートしていますが、**CPython 3 の拡張は直接サポートされていません**。
そのため `python/burp_to_csv.py`（CPython 3）をそのまま import することはできず、
本プラグインは同一アルゴリズムを Jython 向けに再実装しています。

### 挙動の一致（パリティ）について
本ファイルは、Burp/Java依存の import を `try/except` で分離する設計になっており
（`ON_JYTHON` フラグ）、**分類・Aura集約キー計算・ワード照合ロジック**の部分は
Burp環境が無くても Python 3 で直接 import して動作します。この性質を利用し、
`python/sample_burp_packets.xml` を対象に、本プラグインのロジックと
`burp_to_csv.py` の実際の出力（`packets.csv`）を突き合わせるパリティ検証を実施し、
**全19パケットで 分類／AggKey／AggRole／Vuln-No が完全一致すること**を確認済みです。
さらに、以下の合成テストでも両ファイルが同一の結果を返すことを確認済みです。
- 同一AggKeyの通信を離れた位置に配置（間に別のAura SPA通信を挟む）→ 離れた側は別グループ／単独になる
- descriptorを持たない同一内容（`auraCmpDef`等）のAura SPA通信を隣接配置 → 集約対象になる
- 同じくdescriptorを持たないが**内容（パラメータの値）が異なる**Aura SPA通信を隣接配置 →
  集約対象にならず単独のまま
- ワード照合の対象を、レスポンスにのみ存在する語で構成 → ヒットしない（レスポンス非対象の確認）

ただし、これは「共通ロジック部分」の検証であり、**Burp API 呼び出し部分（GUI・
`IMessageEditorTab`・`IContextMenuFactory`・Comment/Highlightの読み書き等）は
実際の Burp Suite Pro 環境での動作確認ができていません**（本開発環境に
Burp/Jython実行環境が無いため）。初回導入時は、以下の手順で必ず動作確認してください。

### 初回導入時の確認手順
1. Extensions に Add → **エラーなくロードされること**（Errors タブ確認）
2. `python/word.csv` を [ルール]タブ上段（① リクエスト用ルール）の [CSVロード...] →
   **ルール表に正しく展開されること**（下段の② レスポンス用ルールにも別途同じ手順でロードできる
   ことを確認する）
3. Aura通信（`/sfsites/aura`）を含むページを閲覧 → 選択パケットに **"SF Vuln/Agg"** タブが出現し、
   Descriptors/Objects/AggKeyが表示されること
4. 同一フォームへの逐次入力等で複数のAura通信を**連続して**発生させる → [解析]タブで[解析更新] →
   対象パケットを選択し **"SF Vuln/Agg"** タブで「代表」「集約対象」に判別されること
   （[解析]タブの「種別ごとの集計」は件数のサマリーのみのため、個々のAggRoleはここでは確認できません）
4b. 同じフォームテストを**別の操作を挟んで**もう一度実施する → 解析更新後、
   **1回目と2回目が別々の集約グループ（1回目の最後は代表のまま等）になり、
   1つの大きなグループに混ざらないこと**（隣接性の条件の確認）
5. `/cst/s/otc` のようなAura以外の通信を複数回発生させる（別トークン等）→ 解析更新後、
   **同一method+pathでも常に「単独」になり、誤って集約されないこと**
5b. `auraCmpDef`/`auraResources`のような、descriptorを持たないAura SPA通信（GET）を
   同じ内容で連続して発生させる → 解析更新後、**集約対象として判別されること**。
   逆に、内容（読み込むコンポーネント等）が異なる同種の通信が隣接している場合は
   **単独のままになること**
6. [集約対象に予約色を適用] → history上で集約対象のみ予約色になり、既存の色分けが保持されること
7. [全history採番] → Comment欄先頭に番号 → [解析]タブで[解析更新]を再実行 →
   [解析結果をCommentへ追記] → 各パケットのComment末尾に `[SF Agg=...]` が付き、
   集約対象パケットには `→代表[0005]` のように代表の採番番号が入ること。
   再度押しても重複しないこと（冪等）
8. **Save items(XML)** → `burp_to_csv.py` 実行 →
   `packets.csv` の No/Comment/AggKey/AggRole/Vul-No が本プラグインの表示と一致すること
9. [解析]タブの**種別ごとの集計**：採番範囲を空欄のまま[表示を更新]→全件が分類ごとに
   カウントされること。採番済みの番号で範囲（例: 開始のみ指定）を入れて再度[表示を更新]→
   件数が絞り込まれ、未採番のパケットは対象外になること。**同時に下のワード照合一覧の
   件数・内容も同じ範囲に絞り込まれること**。集約対象（同一操作の繰り返し）を発生させた
   状態で確認すると、「画面更新(SPA)」の**「含む」列が「除く」列より大きくなり**、
   画面／API／静的は**両列が常に同じ値**になること
9b. ワード照合一覧の **[集約対象を除いて表示]** は既定でONです。解析更新直後の一覧に
   AggRole「集約対象」の行が出ていないこと（代表・単独のみ）を確認する。チェックを外すと
   集約対象も含めた全件表示になり、再度チェックすると元に戻ること
9d. ワード照合一覧の、ヒットが複数あるパケットの行を1つクリック → 「選択行: ヒットした
   ワードとロケーション」欄に、`ロケーション | ヒットしたワード` の2列で、ヒット件数分の
   行が並ぶこと（1行に詰め込まれていないこと）。「選択行: ルールComment」欄には長文でも
   折り返して表示されること。別の行をクリックすると内容が切り替わること。**分類**列に
   画面／画面更新(SPA)／API／静的のいずれかが表示されていること
9e. word.csv に、絶対にヒットしないダミーのVuln-No（例: 存在しない単語のルール）を1件
   追加してロード → [解析更新] 実行後、[ルール]タブの表でそのルールの「ヒット状況」列が
   「★ 未ヒット」・「ヒット数」列が `0` になり、他のヒットしたルールは「ヒットあり」・
   実際にヒットしたパケット数が表示されること
9f. ② レスポンス用ルール（下段）にレスポンス本文中の文字列（例: エラーメッセージの一部）を
   ヒットさせるルールを1件ロード → 上段（リクエスト用）とは異なる結合条件（AND/OR）を設定
   → [解析更新] 実行後、下段の表だけに「ヒットあり」が付き、上段のヒット状況・ヒット数には
   影響しないこと。同じVuln-Noを上段・下段の両方に定義した場合、[解析]タブのワード照合一覧・
   "SF Vuln/Agg"タブでは1件のVuln-Noとして、両方のロケーションのヒットがまとめて
   表示されること
9c. **[Burp Target Scope 内のみを解析対象にする]** は既定でONです。**先にBurpの
   Target タブでScope（診断対象）を設定してから** [解析更新] してください。
   Scope未設定のまま[解析更新]すると結果が0件になり、ログに「全件がScope外と
   判定されました」と出ること（意図した挙動）。Scopeを設定した状態で[解析更新]すると、
   Scope外の通信が集計・一覧から消え、ログに「Scope外 N 件を除外」と出ること。
   チェックを外して再度[解析更新] → 全件が対象に戻ること
10. **コックピット**タブ → [▶ Auto実行] を押す → まずルールインポート状況の確認ダイアログが
    出ること（ルール未読み込みなら警告表示、読み込み済みなら件数が表示されること）。
    チェックを両方外した状態でOKすると、採番・解析更新・Commentへの追記が順番に実行され、
    ログに各ステップの完了メッセージが出ること。「追加コメント全クリア」にチェックを
    入れて実行した場合は、続けてもう一つ確認ダイアログが出ること

### ハイライト色について
Burpが受け付ける色は `red, orange, yellow, green, cyan, blue, pink, magenta, gray` です。
**予約色は、診断中にご自身が手動で色分けに使っていない色を選んでください。**
「予約色のみクリア」は、現在その色になっているセルのみを対象にするため、
他の色を意図的に使い分けている場合でも安全に使えます。

### 送信・通信について
[ルール]・[コックピット]・[解析]・[採番]・[集約色]の各タブは、Burpが既に保持している
history のデータを注釈・表示するのみで、外部への送信は一切行いません。

**[Aura診断]タブのみ例外です。** このタブは対象ホストへ実際にHTTPリクエストを送信します
（詳細は本ドキュメント前半の「Aura診断 タブ（能動送信）」を参照）。送信は以下の条件でのみ
発生します。

- タブ最上部の**「アクティブ送信を有効にする」**チェックを明示的にONにしていること
- ①でユーザーが**対象を明示的に設定**していること（自動で対象が決まることはない）
- ②偵察・③データ抽出とも、**ボタン操作によるオンデマンド実行**のみ（自動的・継続的に
  送信し続けることはない）。③データ抽出は、実行前に対象ホスト・対象オブジェクトを
  示す確認ダイアログでの承認が必須

**[Aura診断]タブは、認可された脆弱性診断対象に対してのみ使用してください。** 未認可の
ホストに対して実行すると、不正アクセス行為に該当するおそれがあります。

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| Extension のロードに失敗する | Jython Standalone JAR のパス設定（Extender → Options）を再確認 |
| "SF Vuln/Agg" タブが出てこない | Aura通信でない、またはワードリストに何もヒットしていない場合は非表示になります（仕様） |
| AggRoleが「未解析」のまま | [解析]タブで [解析更新] を実行してください |
| 集約色ボタンを押しても変化がない | 先に [解析更新] を実行したか確認。予約色が他の意図と重複していないか確認 |
| CSVロードでルールが0件になる | ヘッダ行の判定（列名に"vul"を含むか）／区切り文字が `,` か確認 |
| comment列の日本語が `ã«ã¯...` のように文字化けする | UTF-8/cp932 以外の文字コードで保存されている可能性があります。Excel等で保存し直す場合は「CSV UTF-8（コンマ区切り）」形式を推奨します |
| burp_to_csv.py の結果と一致しない | 双方とも「同時点のhistory」に対して実行しているか確認（後からトラフィックが増えるとNoがズレます） |
| [表からルール反映]を押しても実行ログに何も出ず、日本語のcommentを入れたルールがヒットしない | 古いバージョンの症状です。最新版では、セル編集中でも入力内容が確実に反映され、日本語等の非ASCII文字を含むセルでも例外にならず正常に動作します |
